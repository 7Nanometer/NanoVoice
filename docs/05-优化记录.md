## 二、致命问题

### 问题 1：运行环境损坏，系统完全无法启动

**现象**

```
> venv\Scripts\python.exe --version
No Python at '"D:\PYTHON\python.exe'
（退出码 103）
```

**原因分析**

项目使用虚拟环境（venv）隔离依赖。虚拟环境不保存 Python 本体，
只记录"本体在哪里"——配置文件中写着 `home = D:\PYTHON`。
由于该路径下的 `python.exe` 已被删除（目录仍在，但只剩残留子目录），
虚拟环境失去依赖，任何调用都会失败。

**修改方式**

经评估后改为使用系统级 Python 3.13 环境，并输出 `requirements.txt` 锁定版本：

```
pip install -r requirements.txt
```

同时补充了 Python 3.13 的兼容性适配（见问题 2）。

**验证**：`python check_env.py` 全部 21 项通过。

### 问题 2：主配音功能在默认参数下必然失败

**现象**

界面默认设置（语速 0、音量 0）下点击"合成配音"，必然报错：

```
第 1 段音频生成失败: Invalid rate '0%'.
```

11 个可选声音中有 10 个（全部微软在线音色）受影响。

**原因分析**

原代码的参数拼接逻辑：

```python
rate_str = f"+{rate}%" if rate > 0 else f"{rate}%"
volume_str = f"+{volume}%" if volume > 0 else f"{volume}%"
```

滑杆默认值为 0，`0 > 0` 为假，因此走 else 分支拼出 `"0%"`。

而 edge-tts 库对这两个参数的正则校验为 `^[+-]\d+%$` —— **必须带正负号**。
实测验证：

| 传入值 | 结果 |
|---|---|
| `'0%'` | ❌ `Invalid rate '0%'` |
| `'+0%'`（配 `+0%` 音量） | ✅ 通过 |
| `'+5.0%'` | ❌ `Invalid rate '+5.0%'`（不接受小数） |

即：默认参数 100% 触发失败；且即使调大滑杆，若库返回浮点数仍会失败。

**修改方式**

统一格式化函数，强制"带符号 + 整数"：

```python
def _fmt_signed_percent(value) -> str:
    return f"{int(round(float(value))):+d}%"
```

| 输入 | 输出 |
|---|---|
| `0` | `'+0%'` |
| `5` | `'+5%'` |
| `-8` | `'-8%'` |
| `5.0` | `'+5%'` |

**验证**：默认参数下实际调用微软接口，成功生成 16416 字节音频文件。

### 问题 3：局域网内任意设备可下载 API 密钥

**现象**

界面启动参数为：

```python
demo.launch(server_name="0.0.0.0", allowed_paths=["."], ...)
```

**原因分析**

两个设置叠加导致严重信息泄露：

1. `server_name="0.0.0.0"` —— 监听所有网络接口，同一局域网内任何设备都能访问
2. `allowed_paths=["."]` —— 把**当前目录设为可下载白名单**。Gradio 的机制是：
   传入目录则"该目录下所有文件对所有用户可访问"

且未设置任何身份验证。三者叠加后的后果：同一 WiFi 下的任何人
访问 `http://<本机IP>:7860/file=.env` 即可直接下载到 `.env` 文件，
从中获取明文的 API 密钥。

**修改方式**

采用三层防护：

```python
demo.launch(
    server_name=config.APP_HOST,              # 默认 127.0.0.1，仅本机可访问
    allowed_paths=[str(config.OUTPUT_DIR)],   # 只放行输出目录
    blocked_paths=[str(config.ROOT / ".env")],# 黑名单兜底
    auth=(user, password) if 对外访问 else None,
)
```

**验证方法**

| 请求 | 修改前 | 修改后 |
|---|---|---|
| `http://127.0.0.1:7860/file=.env` | 200（可下载） | 403（拒绝） |
| `http://<局域网IP>:7860/` | 可访问 | 连接失败 |
| `http://127.0.0.1:7860/file=outputs/audio/xxx.mp3` | 200 | 200（正常下载不受影响） |

**后续处理**：由于密钥曾处于暴露状态，建议重新生成密钥。

## 三、严重问题

### 问题 4：自行训练的语音模型从未被使用

**现象**

系统启动参数为：

```
-s ...\pretrained_models\v2Pro\s2Gv2Pro.pth
-g ...\pretrained_models\s1v3.ckpt
```

这两个都是**出厂底模**（未学习过任何目标音色）。
而 2026 年 6 月训练的 `7Nanometer` 模型权重一直保存在磁盘上未被加载。

**原因分析**

GPT-SoVITS 的语音克隆由两个模型配合完成：
- SoVITS（声学模型）决定音色相似度
- GPT（语气模型）决定语调自然度

训练产出保存在独立的权重目录（`SoVITS_weights_v2Pro/`、`GPT_weights_v2Pro/`），
与底模目录（`pretrained_models/`）不同。启动脚本填写的是底模路径，
因此系统实际运行在"底模 + 参考音频零样本克隆"模式，
训练成果完全闲置。

**修改方式**

```python
"-s", str(config.SOVITS_WEIGHT),   # 7Nanometer_e8_s272.pth
"-g", str(config.GPT_WEIGHT),      # 7Nanometer-e15.ckpt
```

权重路径集中在 `config.py`，并支持通过 `.env` 切换，
便于做不同训练轮次的对比实验。

**验证**

1. 查看运行中进程的命令行参数，确认 `-s` / `-g` 指向训练权重 ✅
2. 全项目检索底模文件名，无残留引用 ✅
3. **对照实验**：同一段文字分别用底模和训练模型生成音频

   | 文件 | 时长 | 大小 |
   |---|---|---|
   | `对比_1_出厂底模.mp3` | 16.4 秒 | 198 KB |
   | `对比_2_我训练的模型.mp3` | 13.6 秒 | 164 KB |

   两者时长和文件大小差异明显，证明模型切换确实生效。

### 问题 5：参考音频对应的文本是占位符

**现象**

启动参数中参考文本写的是：

```
-dt "测试语音克隆"
```

**原因分析**

GPT-SoVITS 的 `prompt_text` 参数必须与参考音频中**实际说出的内容**一致，
引擎依靠它对齐音素与声学特征。文本与音频不符会导致韵律和音色明显偏移。

从训练记录 `logs/7Nanometer/2-name2text.txt` 中查到该参考音频的真实内容为：

> 大有克阳这个名字大家应该并不陌生.一九八零年,二十六岁的大有克阳,凭借着童梦这部作品获得了第四届日本大赏.

**修改方式**

将 `REF_TEXT` 改为真实文本，并集中配置在 `config.py`。

**验证**：服务启动日志中确认加载了正确的参考文本。

### 问题 6：健康检查实际执行了完整语音推理

**现象**

服务状态检查的接口调用为：

```python
session.get(API_URL + "/?text=test&text_language=all_zh", timeout=5)
```

**原因分析**

GPT-SoVITS 的 `GET /` 路由会走完整的推理流程。因此每次"检查状态"
都相当于**真的合成一段音频** —— 消耗 GPU 算力、耗时数秒。
而超时仅设置为 5 秒，服务正常但正忙时会误判为"未连接"。

此外，界面在**构建阶段**就同步调用了该检查，导致界面启动被阻塞数秒。

**修改方式**

改探 `/docs`（Web 框架自带的接口文档页，纯静态，不触发任何推理）：

```python
response = session.get(url + "/docs", timeout=3)
```

界面构建阶段改用本地端口探测（毫秒级）。

**验证**

| 指标 | 修改前 | 修改后 |
|---|---|---|
| 单次探活耗时 | 数秒（含完整推理） | 约 2 毫秒 |
| 连续 10 次探活总耗时 | 数十秒 | 0.02 秒 |
| 探活期间 GPU 占用变化 | 明显上升 | 无变化 |
| 界面启动阻塞 | 约 5 秒 | 无 |

## 四、中等问题

### 问题 8：多篇文章分隔符会被正文内容误触发

**原因**：使用 `'---'` 作为分隔符，而网页正文中经常出现 `---`（Markdown 分隔线）。
结果一篇文章被误切为多篇。

**修改**：改用整行标记 `======== 文章分隔 ========`，并用行首行尾锚定的正则切分：

```python
_SEP_PATTERN = re.compile(r"^\s*={4,}\s*文章分隔\s*={4,}\s*$", re.MULTILINE)
```

**验证**：构造含 `---` 的正文，确认不再误切（正确切出 2 篇）。

### 问题 9：抓取失败信息被当作文章内容送入大模型

**原因**：抓取函数出错时返回字符串 `"提取失败: xxx"`，与正常正文无法区分，
会一并被送入大模型的提示词。

**修改**：改为返回 `(是否成功, 内容或错误)` 二元组，失败信息单独显示在状态栏。

### 问题 10：输出文件名固定导致互相覆盖

**原因**：输出固定为 `final_audio.mp3`，中间文件固定为 `temp_{i}.wav`。
重复点击或并发使用会互相覆盖。

**修改**：

```python
def new_output_path(prefix="配音", ext="mp3") -> Path:
    stamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    return config.AUDIO_DIR / f"{prefix}_{stamp}_{uuid.uuid4().hex[:4]}.{ext}"
```

中间文件每次任务使用独立临时目录，任务结束整目录删除。

**验证**：连续生成两次，输出目录产生两个不同文件。

---

### 问题 11：无标点的超长句未被切分

**原因**：分块逻辑只按标点断句，若某"句"本身超长（如长串无标点文本），
会整块送入引擎，导致显存占用过高甚至超时。

**修改**：增加硬切兜底 —— 超过阈值的长句按字数强制切分。
同时将本地克隆的单块上限从 300 字降至 100 字（更稳定、停顿更自然）。

---

### 问题 12：音频导出参数冲突

**原因**：`export(bitrate="192k", parameters=["-q:a", "0"])` ——
同时指定固定码率和可变码率质量参数，二者冲突，实际以 VBR 为准。
且对 32kHz 单声道人声而言 192k 过高。

**修改**：改为 `bitrate="96k"`，移除冲突参数。

**效果**：10 分钟音频体积由 9.7MB 降至约 7MB。

---

### 问题 13：提示词结构标记被朗读出来

**原因**：给大模型的提示词要求文案分"开头/中间/结尾"，模型将结构标记
（如 `【开头：抓住眼球】`）写入了正文，语音合成时被一字不差地念出。

**修改**：双重防护 ——
① 提示词中增加硬约束"只输出可直接朗读的正文，不要输出任何【】标记"；
② 合成前增加清洗函数，移除 `【】` 标记、Markdown 符号和行首序号。

### 问题 14：模型名硬编码三处

**修改**：统一由 `config.LLM_MODEL` 提供。

### 问题 15：错误堆栈直接显示在界面上

**原因**：异常处理时将 `traceback.format_exc()` 拼接进返回值，
在界面上显示完整的技术堆栈（含本机绝对路径）。

**修改**：详细堆栈只写入日志文件，界面只显示经过翻译的友好提示
（如"账户余额不足，请去官网充值"）。

### 问题 16：查找音色失败时静默降级

**原因**：`next((v for v in voices if ...), {"voice": "zh-CN-YunxiNeural"})` ——

### 问题 18：设置 no_proxy 反而把系统代理整个关掉了

> 这是**端到端测试阶段才暴露的问题**，改造前的代码里就已经存在。

**现象**

网页抓取功能对境外站点全部失败：

```
第1条「https://example.com」抓取失败：连不上这个网址
```

但用同样的 Python 环境单独执行 `requests.get('https://example.com')` 却能成功。

**原因分析**

原代码中有这样一行（目的是让本机地址不走代理）：

```python
os.environ['no_proxy'] = 'localhost,127.0.0.1'
```

看起来合理，但 Python 的代理探测函数是这样实现的：

```python
def getproxies():
    return getproxies_environment() or getproxies_registry()
```

逻辑是：**先看环境变量，只要环境变量里有任何一个以 `_proxy` 结尾的变量，
就直接返回，根本不去读操作系统的代理设置**。

而 `no_proxy` 恰好也以 `_proxy` 结尾。实测对比：

| 环境 | `getproxies()` 返回值 | 访问境外站点 |
|---|---|---|
| 不设任何环境变量 | `{'http': '...7897', 'https': '...7897'}` | ✅ 200 |
| 只设 `no_proxy` | `{'no': 'localhost,127.0.0.1'}` | ❌ ConnectionError |

即：为了排除一个本机地址，把整个代理配置都作废了。

**修改方式**

删除该环境变量的设置。本机地址不走代理的需求，
改由请求会话的 `session.trust_env = False` 实现——
那个会话完全不参考任何代理设置，语义更准确、没有副作用。

```python
# 语音服务的会话：不读代理，直连本机
session = requests.Session()
session.trust_env = False

# 网页抓取：使用系统代理，保证能访问境外站点
response = requests.get(url, headers=HEADERS, timeout=(5, 30))
```

**验证**

| 目标 | 修改前 | 修改后 |
|---|---|---|
| `https://example.com`（境外） | ❌ 连接失败 | ✅ 成功抓取 171 字 |
| 故意填写的错误网址 | 报错信息混入正文 | 正确显示在状态栏 |
| 访问本机语音服务 | ✅ | ✅ 不受影响 |

| 迁移能力 | 换盘符后自检 | 全部通过 |

## 八、功能改进：文章输入方式

### 改造前

「文章内容」是一个纯文本框，只能手动粘贴，且多篇文章必须用
`======== 文章分隔 ========` 手工隔开。实际使用时：

- 手边已有的 Word 文档、txt 文件要先打开、全选、复制，再粘贴
- 多篇内容要自己敲分隔标记，容易漏、容易错
- 粘贴长文时格式会丢失

### 改造后

引入 `file_reader.py` 模块，支持**直接拖入文件**：

| 方式 | 说明 |
|---|---|
| **拖入文件**（新增，主推） | 一个文件算一篇文章，可一次拖多个 |
| 从网址抓取 | 收进折叠区，抓取结果自动参与生成 |
| 手动粘贴 | 收进折叠区，保留作为备用 |

三种方式的内容会**合并**后一起送入大模型，互不冲突。

### 技术要点

**1. 文件格式与依赖**

| 格式 | 处理方式 |
|---|---|
| `.txt` / `.md` | 直接读字节流 |
| `.docx` | 借助 `python-docx` 提取段落和表格 |

界面上通过 `gr.File(file_types=[...])` 限制可拖入的格式，
拖入不支持的文件会在上传阶段就被拒绝（实测提示：
`Invalid file type. Please upload a file that is one of these formats`），
`file_reader.py` 里的格式校验作为第二道保险。

**2. 中文编码自动识别（关键难点）**

中文纯文本文件的编码不统一：老文件多为 GBK，新文件多为 UTF-8，
带 BOM 的 UTF-8 又是第三种。读错编码会导致整篇乱码。

处理策略是**逐种尝试**，并优先识别 BOM：

```python
if raw.startswith(b"\xef\xbb\xbf"):      # UTF-8 BOM
    return raw.decode("utf-8-sig")
if raw.startswith((b"\xff\xfe", b"\xfe\xff")):  # UTF-16 BOM
    return raw.decode("utf-16")

for enc in ["utf-8", "utf-8-sig", "gbk", "gb18030", "big5", "latin-1"]:
    try:
        return raw.decode(enc)
    except UnicodeDecodeError:
        continue
```

实测：一个 GBK 编码的中文文件被正确读出，无乱码。

**3. Word 文档提取**

`.docx` 本质是打包的 XML，不是纯文本。除了正文段落，
还提取了**表格内容**（很多人把资料整理在表格里），
并对合并单元格产生的重复内容去重。

**4. 读取反馈**

拖入文件后立即显示每个文件读到了多少字，
读失败的会明确说明原因（空文件 / 格式不支持 / 文件不存在），
避免"以为读进去了其实没有"。

### 验证结果

| 测试项 | 结果 |
|---|---|
| UTF-8 文本文件 | ✅ 66 字 |
| **GBK 编码中文文件** | ✅ 58 字，无乱码 |
| Word 文档（含表格） | ✅ 111 字，表格内容正确提取 |
| Markdown 文件 | ✅ 41 字 |
| 空文件 | ✅ 明确提示"文件里没有文字内容" |
| 不支持的格式 | ✅ 上传阶段即被拦截 |
| 未拖入文件 | ✅ 提示如何操作 |
| **端到端：拖入 2 个文件生成文案** | ✅ 成功，且内容确实**融合了两篇**——前半段来自 txt（教育话题），后半段来自 Word 文档（大语言模型、影像辅助诊断） |

### 附带修复

测试过程中发现：**端口被占用时程序会抛出大段英文异常堆栈然后崩溃**。
用户双击两次 `start.bat` 就会遇到。已改为友好的中文提示，
并给出具体的排查步骤。

## 九、问题修复：生成文案的字数与目标严重不符

> 这是**实际使用中暴露的问题**（目标 4500 字，生成出 7550 字，超出 68%）。

### 现象

界面设置目标字数 4500，生成的文案却是 7550 字。

### 排查过程

**第一步：查日志，确认纠偏机制是否触发**

```
14:34:47  本次生成使用 6 篇文章（文件 6 篇）
14:35:08  字数 7550 偏离目标 4500，请求模型调整一次
14:35:26  文案生成完成：7550 字（目标 4500）
```

纠偏调用确实执行了（耗时 18 秒），但字数**一个字都没变**。

**第二步：用真实数据复现**

项目自动存档了那次生成的原文，直接用它复现纠偏调用，得到关键证据：

```
返回内容长度: 7638，去掉空白后: 7550   ← 和输入完全一样
completion_tokens: 4531
```

模型把原文**原样抄了一遍**。再看当时的纠偏提示词：

> "保持内容完整性和主题不变，只调整篇幅"

**问题找到了**：提示词自相矛盾——既要求"保持内容完整"，又要求"压缩到 4500 字"。
模型选择保住内容，所以一个字没删。

**第三步：系统性测试各种提示词方案**

改了 5 种写法逐一实测，目标都是把 7550 字压到 4500：

| 方案 | 结果 | 偏差 |
|---|---|---|
| 原写法 | 7550 字 | +67.8% |
| 明确要求删减 | 6985 字 | +55.2% |
| 删减 + 收紧额度 | 7275 字 | +61.7% |
| 分 6 段各约 750 字 | 7111 字 | +58.0% |
| 指定每段主题 | 7107 字 | +57.9% |

**结论：改提示词治不了这个病。** 模型只要看到大量素材，就会一直写下去。

**第四步：定位真正的控制手段**

从 `completion_tokens` 数据算出换算关系：**中文约 1.67 字 / token**。

而原代码的额度算法是：

```python
max_tokens = int(word_count * 1.8)      # 4500 字 → 8100 token → 约 13500 字的空间
```

**对 4500 字的目标，它给了能写 13500 字的额度——等于没有限制。**

实测验证：把额度精确收紧后，模型会**写到额度上限就停**，
输出长度与额度几乎线性对应。也就是说，**物理额度才是可靠的字数控制手段**。

### 修改方式

**核心思路：不靠"求它写短"，而靠"只给它够用的额度"。**

```python
CHARS_PER_TOKEN = 1.67       # 实测换算比

def _tokens_for_chars(chars, margin=1.05):
    return max(64, min(int(chars / CHARS_PER_TOKEN * margin), 8000))
```

配套两项收尾处理，解决"写满即停"带来的副作用：

**（1）结尾被切断 → 裁到完整的句子**

模型写到额度上限会戛然而止（如"…总感觉词不达意，或是以"）。
裁到最后一句句末标点，保证结尾完整。

**（2）篇幅不够 → 顺着语气补写**

实测发现模型的行为是**双向的**：有时写超，有时写不足。
比目标少 8% 以上时，取末尾 600 字发给模型，请它接着写并自然收尾
（不需要把全文再传一遍，省额度也更快）。

### 验证结果

| 场景 | 目标 | 实际 | 偏差 | 结尾完整 |
|---|---|---|---|---|
| 短素材 · 小目标 | 300 字 | 289 字 | −3.7% | ✅ |
| 短素材 · 中目标 | 800 字 | 857 字 | +7.1% | ✅ |
| 长素材 · 中目标 | 1500 字 | 1540 字 | +2.7% | ✅ |
| **长素材 · 大目标（原问题场景）** | **4500 字** | **4479 字** | **−0.5%** | ✅ |

**从偏差 +68% 改善到 ±8% 以内。**

### 可复用的经验

1. **提示词里写"请写 N 字"，模型基本不会照做**——尤其当输入素材远超目标长度时
2. **可靠的字数控制靠输出额度（max_tokens）**，按实测换算比精确计算
3. **"压缩已有长文"是模型的弱项**——它倾向于保留原内容，改提示词也收效有限
4. **模型行为是双向的**，超出和不足都要处理，只防一头会在另一种情况失灵

## 十、模型重训：解决"沙哑、残缺、无情感波动"

> 这是**实际使用中暴露的问题**：语音克隆的成品句子有残缺、声音沙哑、没有情感起伏。

### 排查过程

按"先测量、再归因"的顺序逐项排除：

| 怀疑对象 | 测量方法 | 结论 |
|---|---|---|
| 音频削波（我最初的怀疑） | 逐样本统计达 ±32767 的数量 | ❌ 2239 万样本中仅 13 个，占 0.000% |
| 分块丢字 | 分块后重新拼接与原文对比 | ❌ 4540 字进、4540 字出，零丢失 |
| 响度处理压扁动态 | 测量有声帧的音量分布 | ❌ 动态范围 8.3 dB，与素材 8.9 dB 相当 |
| 推理参数没调好 | 试 12 组参数组合 | ❌ 同参数重复跑底噪在 −54~−71 dB 乱跳，参数不是决定因素 |

**关键对照实验**（同一句话、同一参数，只换模型）：

| 模型 | 底噪 | 语速 | 过零率 |
|---|---|---|---|
| 出厂底模 | −76.6 dB | 4.95 字/秒 | 0.027 |
| 自己的训练模型 | **−55.1 dB** | **5.53 字/秒** | **0.035** |

训练模型的底噪比**原始训练素材本身**（−60.8 dB）还高——说明它在**自己制造噪声**。

**根因**：训练量严重不足。

| 项目 | 原训练 |
|---|---|
| 训练片段 | 126 条 |
| 训练轮数 | 8 轮 |
| 总步数 | 约 256 步 |
| **训练总耗时** | **约 3 分钟** |

### 重训方案

**第一步：音频清理**

分析发现素材的噪声集中在 100 Hz 以下（78/94/62/31/47 Hz 的峰），
是电源嗡声一类的低频噪声，不是背景音乐。

处理链：`highpass=f=80, afftdn=nr=12:nf=-40:tn=1`

| 指标 | 处理前 | 处理后 |
|---|---|---|
| 80Hz 以下能量占比 | 1.92% | **0.93%**（降 52%） |
| 底噪 | −74.5 dB | −76.2 dB |
| 人声电平损失 | — | 仅 0.1 dB |

**第二步：重新切片**

把 126 条扩到 **165 条**（+31%），平均 4.8 秒/条。

**第三步：重新训练**

轮数 8 → **25 轮**，训练步数约 256 → **约 1050 步**（4 倍）。

### 过程中发现并解决的技术问题

**问题 A：切片参数传错，切出来的全是白噪声**

切片脚本的参数 `_max` 是**音量归一化目标**（正确值 0.9），
被误当成"最长时长"传了 9000，音频被放大 8100 倍后 int16 溢出，
全部变成满量程白噪声。

- 检验方法：**计算切片文件与源音频的相关系数**（正常应接近 1）
- 修复前：相关系数 ≈ 0（完全无关）
- 修复后：相关系数 = 1.000

**这个问题极其隐蔽**：语音识别模型还从噪声中"识别"出了 115 条文字（幻觉），
如果只看识别结果而不做相关性校验，会拿着纯噪声去训练。

**问题 B：数据格式不匹配导致训练集为空**

`1-get-text.py` 和 `3-get-semantic.py` 的输出文件带分片编号
（`2-name2text-0.txt`、`6-name2semantic-0.tsv`），
而训练加载器读取的是不带编号的文件名。改名后才正常加载。

**问题 C：内存不足导致训练中断**

训练脚本默认开 5 个数据加载进程（`num_workers=5`，且 `prefetch_factor=3`），
内存峰值超过 5.6 GB，而机器仅剩约 6 GB 可用，报出
`MemoryError` / `CUDA error: resource already mapped` / `CUDA out of memory`
三个看似不同、实为同源的错误。

调整为 `num_workers=2`（**只影响数据读取速度，不影响训练结果**）后正常。

### 重训效果（客观测量）

每个模型测 3 次取平均，用**声纹识别模型**测量音色相似度：

| 模型 | 音色相似度 ↑ | 底噪 ↓ | 语速 |
|---|---|---|---|
| 出厂底模 | 0.850 | −76.1 dB | 4.94 字/秒 |
| 旧模型（8 轮） | 0.848 | −55.2 dB | 5.53 字/秒 |
| 新模型（15 轮） | 0.854 | **−63.4 dB** | 5.36 字/秒 |
| **新模型（25 轮）** | **0.899** | −61.6 dB | 5.47 字/秒 |

**结论**：

1. **旧模型（8 轮）的音色相似度（0.848）甚至低于出厂底模（0.850）**——
   训练量不足不仅没提升音色，还引入了噪声，等于白做
2. **新模型（25 轮）两项指标全面优于旧模型**：音色相似度 +0.051，底噪改善 6.4 dB
3. 15 轮与 25 轮各有侧重（15 轮更干净，25 轮更像），最终选用 25 轮

### 遗留的客观差距

新模型的底噪（−61.6 dB）仍比出厂底模（−76.1 dB）高 14.5 dB。
这是**训练素材本身的限制**——素材是从 128 kbps MP3 中提取的 13.5 分钟录音，
质量上限就在那里。要根本改善需要更高质量的录音素材。

### 可复用的经验

1. **训练量不足比参数没调好严重得多**：8 轮（3 分钟）和 25 轮（16 分钟）的差距是数量级的
2. **"像不像"和"干不干净"可以客观测量**，不必只靠耳朵判断——声纹模型测相似度，
   静音段电平测底噪
3. **合成类任务的中间产物必须做来源校验**：切片文件要验证与源音频的相关性，
   否则错误的数据会一路静默传递到训练
4. **同一模型多次生成的差异可能大于模型之间的差异**，对比实验必须重复多次取平均
