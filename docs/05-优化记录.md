## 二、致命问题

### 问题 1：运行环境损坏，系统完全无法启动

**现象**

```
> venv\Scripts\python.exe --version
No Python at '"D:\PYTHON\python.exe'
（退出码 103）
```

**原因分析**

项目使用虚拟环境（venv）隔离依赖。虚拟环境不保存 Python 本体，
只记录"本体在哪里"——配置文件中写着 `home = D:\PYTHON`。
由于该路径下的 `python.exe` 已被删除（目录仍在，但只剩残留子目录），
虚拟环境失去依赖，任何调用都会失败。

**修改方式**

经评估后改为使用系统级 Python 3.13 环境，并输出 `requirements.txt` 锁定版本：

```
pip install -r requirements.txt
```

同时补充了 Python 3.13 的兼容性适配（见问题 2）。

**验证**：`python check_env.py` 全部 21 项通过。

### 问题 2：主配音功能在默认参数下必然失败

**现象**

界面默认设置（语速 0、音量 0）下点击"合成配音"，必然报错：

```
第 1 段音频生成失败: Invalid rate '0%'.
```

11 个可选声音中有 10 个（全部微软在线音色）受影响。

**原因分析**

原代码的参数拼接逻辑：

```python
rate_str = f"+{rate}%" if rate > 0 else f"{rate}%"
volume_str = f"+{volume}%" if volume > 0 else f"{volume}%"
```

滑杆默认值为 0，`0 > 0` 为假，因此走 else 分支拼出 `"0%"`。

而 edge-tts 库对这两个参数的正则校验为 `^[+-]\d+%$` —— **必须带正负号**。
实测验证：

| 传入值 | 结果 |
|---|---|
| `'0%'` | ❌ `Invalid rate '0%'` |
| `'+0%'`（配 `+0%` 音量） | ✅ 通过 |
| `'+5.0%'` | ❌ `Invalid rate '+5.0%'`（不接受小数） |

即：默认参数 100% 触发失败；且即使调大滑杆，若库返回浮点数仍会失败。

**修改方式**

统一格式化函数，强制"带符号 + 整数"：

```python
def _fmt_signed_percent(value) -> str:
    return f"{int(round(float(value))):+d}%"
```

| 输入 | 输出 |
|---|---|
| `0` | `'+0%'` |
| `5` | `'+5%'` |
| `-8` | `'-8%'` |
| `5.0` | `'+5%'` |

**验证**：默认参数下实际调用微软接口，成功生成 16416 字节音频文件。

### 问题 3：局域网内任意设备可下载 API 密钥

**现象**

界面启动参数为：

```python
demo.launch(server_name="0.0.0.0", allowed_paths=["."], ...)
```

**原因分析**

两个设置叠加导致严重信息泄露：

1. `server_name="0.0.0.0"` —— 监听所有网络接口，同一局域网内任何设备都能访问
2. `allowed_paths=["."]` —— 把**当前目录设为可下载白名单**。Gradio 的机制是：
   传入目录则"该目录下所有文件对所有用户可访问"

且未设置任何身份验证。三者叠加后的后果：同一 WiFi 下的任何人
访问 `http://<本机IP>:7860/file=.env` 即可直接下载到 `.env` 文件，
从中获取明文的 API 密钥。

**修改方式**

采用三层防护：

```python
demo.launch(
    server_name=config.APP_HOST,              # 默认 127.0.0.1，仅本机可访问
    allowed_paths=[str(config.OUTPUT_DIR)],   # 只放行输出目录
    blocked_paths=[str(config.ROOT / ".env")],# 黑名单兜底
    auth=(user, password) if 对外访问 else None,
)
```

**验证方法**

| 请求 | 修改前 | 修改后 |
|---|---|---|
| `http://127.0.0.1:7860/file=.env` | 200（可下载） | 403（拒绝） |
| `http://<局域网IP>:7860/` | 可访问 | 连接失败 |
| `http://127.0.0.1:7860/file=outputs/audio/xxx.mp3` | 200 | 200（正常下载不受影响） |

**后续处理**：由于密钥曾处于暴露状态，建议重新生成密钥。

## 三、严重问题

### 问题 4：自行训练的语音模型从未被使用

**现象**

系统启动参数为：

```
-s ...\pretrained_models\v2Pro\s2Gv2Pro.pth
-g ...\pretrained_models\s1v3.ckpt
```

这两个都是**出厂底模**（未学习过任何目标音色）。
而 2026 年 6 月训练的 `7Nanometer` 模型权重一直保存在磁盘上未被加载。

**原因分析**

GPT-SoVITS 的语音克隆由两个模型配合完成：
- SoVITS（声学模型）决定音色相似度
- GPT（语气模型）决定语调自然度

训练产出保存在独立的权重目录（`SoVITS_weights_v2Pro/`、`GPT_weights_v2Pro/`），
与底模目录（`pretrained_models/`）不同。启动脚本填写的是底模路径，
因此系统实际运行在"底模 + 参考音频零样本克隆"模式，
训练成果完全闲置。

**修改方式**

```python
"-s", str(config.SOVITS_WEIGHT),   # 7Nanometer_e8_s272.pth
"-g", str(config.GPT_WEIGHT),      # 7Nanometer-e15.ckpt
```

权重路径集中在 `config.py`，并支持通过 `.env` 切换，
便于做不同训练轮次的对比实验。

**验证**

1. 查看运行中进程的命令行参数，确认 `-s` / `-g` 指向训练权重 ✅
2. 全项目检索底模文件名，无残留引用 ✅
3. **对照实验**：同一段文字分别用底模和训练模型生成音频

   | 文件 | 时长 | 大小 |
   |---|---|---|
   | `对比_1_出厂底模.mp3` | 16.4 秒 | 198 KB |
   | `对比_2_我训练的模型.mp3` | 13.6 秒 | 164 KB |

   两者时长和文件大小差异明显，证明模型切换确实生效。

### 问题 5：参考音频对应的文本是占位符

**现象**

启动参数中参考文本写的是：

```
-dt "测试语音克隆"
```

**原因分析**

GPT-SoVITS 的 `prompt_text` 参数必须与参考音频中**实际说出的内容**一致，
引擎依靠它对齐音素与声学特征。文本与音频不符会导致韵律和音色明显偏移。

从训练记录 `logs/7Nanometer/2-name2text.txt` 中查到该参考音频的真实内容为：

> 大有克阳这个名字大家应该并不陌生.一九八零年,二十六岁的大有克阳,凭借着童梦这部作品获得了第四届日本大赏.

**修改方式**

将 `REF_TEXT` 改为真实文本，并集中配置在 `config.py`。

**验证**：服务启动日志中确认加载了正确的参考文本。

### 问题 6：健康检查实际执行了完整语音推理

**现象**

服务状态检查的接口调用为：

```python
session.get(API_URL + "/?text=test&text_language=all_zh", timeout=5)
```

**原因分析**

GPT-SoVITS 的 `GET /` 路由会走完整的推理流程。因此每次"检查状态"
都相当于**真的合成一段音频** —— 消耗 GPU 算力、耗时数秒。
而超时仅设置为 5 秒，服务正常但正忙时会误判为"未连接"。

此外，界面在**构建阶段**就同步调用了该检查，导致界面启动被阻塞数秒。

**修改方式**

改探 `/docs`（Web 框架自带的接口文档页，纯静态，不触发任何推理）：

```python
response = session.get(url + "/docs", timeout=3)
```

界面构建阶段改用本地端口探测（毫秒级）。

**验证**

| 指标 | 修改前 | 修改后 |
|---|---|---|
| 单次探活耗时 | 数秒（含完整推理） | 约 2 毫秒 |
| 连续 10 次探活总耗时 | 数十秒 | 0.02 秒 |
| 探活期间 GPU 占用变化 | 明显上升 | 无变化 |
| 界面启动阻塞 | 约 5 秒 | 无 |

## 四、中等问题

### 问题 8：多篇文章分隔符会被正文内容误触发

**原因**：使用 `'---'` 作为分隔符，而网页正文中经常出现 `---`（Markdown 分隔线）。
结果一篇文章被误切为多篇。

**修改**：改用整行标记 `======== 文章分隔 ========`，并用行首行尾锚定的正则切分：

```python
_SEP_PATTERN = re.compile(r"^\s*={4,}\s*文章分隔\s*={4,}\s*$", re.MULTILINE)
```

**验证**：构造含 `---` 的正文，确认不再误切（正确切出 2 篇）。

### 问题 9：抓取失败信息被当作文章内容送入大模型

**原因**：抓取函数出错时返回字符串 `"提取失败: xxx"`，与正常正文无法区分，
会一并被送入大模型的提示词。

**修改**：改为返回 `(是否成功, 内容或错误)` 二元组，失败信息单独显示在状态栏。

### 问题 10：输出文件名固定导致互相覆盖

**原因**：输出固定为 `final_audio.mp3`，中间文件固定为 `temp_{i}.wav`。
重复点击或并发使用会互相覆盖。

**修改**：

```python
def new_output_path(prefix="配音", ext="mp3") -> Path:
    stamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    return config.AUDIO_DIR / f"{prefix}_{stamp}_{uuid.uuid4().hex[:4]}.{ext}"
```

中间文件每次任务使用独立临时目录，任务结束整目录删除。

**验证**：连续生成两次，输出目录产生两个不同文件。

---

### 问题 11：无标点的超长句未被切分

**原因**：分块逻辑只按标点断句，若某"句"本身超长（如长串无标点文本），
会整块送入引擎，导致显存占用过高甚至超时。

**修改**：增加硬切兜底 —— 超过阈值的长句按字数强制切分。
同时将本地克隆的单块上限从 300 字降至 100 字（更稳定、停顿更自然）。

---

### 问题 12：音频导出参数冲突

**原因**：`export(bitrate="192k", parameters=["-q:a", "0"])` ——
同时指定固定码率和可变码率质量参数，二者冲突，实际以 VBR 为准。
且对 32kHz 单声道人声而言 192k 过高。

**修改**：改为 `bitrate="96k"`，移除冲突参数。

**效果**：10 分钟音频体积由 9.7MB 降至约 7MB。

---

### 问题 13：提示词结构标记被朗读出来

**原因**：给大模型的提示词要求文案分"开头/中间/结尾"，模型将结构标记
（如 `【开头：抓住眼球】`）写入了正文，语音合成时被一字不差地念出。

**修改**：双重防护 ——
① 提示词中增加硬约束"只输出可直接朗读的正文，不要输出任何【】标记"；
② 合成前增加清洗函数，移除 `【】` 标记、Markdown 符号和行首序号。

### 问题 14：模型名硬编码三处

**修改**：统一由 `config.LLM_MODEL` 提供。

### 问题 15：错误堆栈直接显示在界面上

**原因**：异常处理时将 `traceback.format_exc()` 拼接进返回值，
在界面上显示完整的技术堆栈（含本机绝对路径）。

**修改**：详细堆栈只写入日志文件，界面只显示经过翻译的友好提示
（如"账户余额不足，请去官网充值"）。

### 问题 16：查找音色失败时静默降级

**原因**：`next((v for v in voices if ...), {"voice": "zh-CN-YunxiNeural"})` ——

### 问题 18：设置 no_proxy 反而把系统代理整个关掉了

> 这是**端到端测试阶段才暴露的问题**，改造前的代码里就已经存在。

**现象**

网页抓取功能对境外站点全部失败：

```
第1条「https://example.com」抓取失败：连不上这个网址
```

但用同样的 Python 环境单独执行 `requests.get('https://example.com')` 却能成功。

**原因分析**

原代码中有这样一行（目的是让本机地址不走代理）：

```python
os.environ['no_proxy'] = 'localhost,127.0.0.1'
```

看起来合理，但 Python 的代理探测函数是这样实现的：

```python
def getproxies():
    return getproxies_environment() or getproxies_registry()
```

逻辑是：**先看环境变量，只要环境变量里有任何一个以 `_proxy` 结尾的变量，
就直接返回，根本不去读操作系统的代理设置**。

而 `no_proxy` 恰好也以 `_proxy` 结尾。实测对比：

| 环境 | `getproxies()` 返回值 | 访问境外站点 |
|---|---|---|
| 不设任何环境变量 | `{'http': '...7897', 'https': '...7897'}` | ✅ 200 |
| 只设 `no_proxy` | `{'no': 'localhost,127.0.0.1'}` | ❌ ConnectionError |

即：为了排除一个本机地址，把整个代理配置都作废了。

**修改方式**

删除该环境变量的设置。本机地址不走代理的需求，
改由请求会话的 `session.trust_env = False` 实现——
那个会话完全不参考任何代理设置，语义更准确、没有副作用。

```python
# 语音服务的会话：不读代理，直连本机
session = requests.Session()
session.trust_env = False

# 网页抓取：使用系统代理，保证能访问境外站点
response = requests.get(url, headers=HEADERS, timeout=(5, 30))
```

**验证**

| 目标 | 修改前 | 修改后 |
|---|---|---|
| `https://example.com`（境外） | ❌ 连接失败 | ✅ 成功抓取 171 字 |
| 故意填写的错误网址 | 报错信息混入正文 | 正确显示在状态栏 |
| 访问本机语音服务 | ✅ | ✅ 不受影响 |
