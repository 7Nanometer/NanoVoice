# 代码结构说明

> 这份文档是**答辩讲稿素材**——把系统怎么跑起来的、每个文件干什么，讲清楚。

---

## 一、整体架构

系统采用**分层 + 模块化**设计，一共 7 个 Python 文件，各司其职：

```
┌─────────────────────────────────────────────────────────┐
│  main.py                          界面层 + 流程调度      │
│  ├─ Gradio 网页界面                                      │
│  ├─ 语音引擎服务进程管理                                  │
│  └─ 把用户操作转交给下面三个业务模块                       │
└─────────────────────────────────────────────────────────┘
              │              │              │
              ▼              ▼              ▼
┌──────────────────┐ ┌──────────────┐ ┌──────────────────┐
│ article_         │ │ script_      │ │ speech_          │
│ extractor.py     │ │ generator.py │ │ synthesizer.py   │
│                  │ │              │ │                  │
│ 网页抓取          │ │ 文案生成      │ │ 语音合成          │
│ requests         │ │ DeepSeek     │ │ ├─ edge-tts      │
│ + BeautifulSoup  │ │ 大语言模型    │ │ └─ GPT-SoVITS    │
└──────────────────┘ └──────────────┘ └──────────────────┘

┌─────────────────────────────────────────────────────────┐
│  config.py    配置层 —— 所有路径/参数的唯一出口           │
│  logger.py    日志层 —— 记录运行过程，便于排障            │
│  check_env.py 运维工具 —— 环境自检                       │
└─────────────────────────────────────────────────────────┘
```

**设计原则**：

1. **配置与代码分离** —— 所有可变项集中在 `config.py`，代码本身不含硬编码路径
2. **业务逻辑与界面分离** —— 三个业务模块不含任何界面代码，可独立测试和复用
3. **失败可观测** —— 关键步骤都有日志记录，错误信息翻译成人话显示给用户

## 二、数据流

从用户输入到成品音频，数据经过 5 个阶段：

```
[1] 输入          网址列表 或 粘贴的文章文本
     │
     ▼
[2] 抓取          article_extractor.extract_text_from_url()
     │             · requests 下载 HTML
     │             · BeautifulSoup 解析、剔除噪声标签
     │             · 优先提取 <article>/<main> 语义标签
     │             · 返回 (是否成功, 正文/错误)
     ▼
[3] 融合          main.split_articles()
     │             · 按 "======== 文章分隔 ========" 切分为多篇
     │             · 合并后统一送入大模型
     ▼
[4] 文案          script_generator.generate_script()
     │             · 组装提示词（风格 + 字数 + 约束）
     │             · 调用 DeepSeek 接口
     │             · 字数偏离超 10% 时自动二次校正
     │             · 存档到 outputs/scripts/
     ▼
[5] 配音          speech_synthesizer.generate_audio_from_script()
                   · sanitize_for_tts()  清除【】标记等不该朗读的内容
                   · split_text_into_chunks()  三级切分
                   · 逐块合成（微软在线 或 本地克隆）
                   · 统一采样率/声道 → 响度对齐 → 插入停顿 → 拼接
                   · 导出 mp3 到 outputs/audio/
     │
     ▼
   成品音频
```

## 三、各模块职责详解

### `main.py` —— 界面与调度（约 430 行）

| 函数 | 职责 |
|---|---|
| `_fmt_signed_percent()` | 把界面滑杆数值转成语音接口要求的格式（**带正负号的整数百分比**） |
| `new_output_path()` | 生成带时间戳的唯一输出文件名 |
| `split_articles()` | 按分隔标记切分多篇文章 |
| `is_port_in_use()` / `kill_process_on_port()` | 端口探测与进程清理 |
| `start_gpt_sovits_service()` | 启动语音引擎，并轮询等待就绪（生成器写法，实时反馈进度） |
| `_warm_up_sovits()` | 预热：提前消化首次推理的模型加载开销 |
| `extract_from_urls()` | 批量抓取，成功的内容与失败信息分开返回 |
| `synthesize_audio()` | 配音主调度，处理参考音频选择、参数校验、结果封装 |

### `article_extractor.py` —— 网页抓取（约 110 行）

核心是 `extract_text_from_url(url, cfg)`，返回 `(是否成功, 内容或错误)` 二元组。

处理要点：
- 超时设置 `(5, 30)` —— 连接 5 秒、读取 30 秒
- `raise_for_status()` 拦截 403/404 等错误响应
- 编码处理：仅在服务器未声明或声明为 ISO-8859-1 时才启用自动探测
- 正文定位：优先 `<article>` / `<main>`，回退整页
- 噪声剔除：移除 script/style/nav/header/footer/aside/form/iframe

### `script_generator.py` —— 文案生成（约 230 行）

| 函数 | 职责 |
|---|---|
| `_client()` | 构造大模型客户端，每次调用重新读取密钥（改配置无需重启） |
| `generate_script()` | 组装提示词 → 调用接口 → 字数校正 → 存档 |
| `refine_script()` | 按用户建议二次改写 |
| `_friendly_error()` | 把技术错误码翻译成用户能看懂的话 |
| `mock_generate_script()` | 演示模式兜底（无密钥时保证界面可用） |

**提示词工程要点**：除了风格和字数要求，还额外约束
"只输出可直接朗读的正文，不要输出任何【】标记、小标题、序号"，
避免结构标记被语音合成念出来。

### `speech_synthesizer.py` —— 语音合成（约 340 行）

| 函数 | 职责 |
|---|---|
| `sanitize_for_tts()` | 清除 `【】`标记、Markdown 符号、行首序号 |
| `split_text_into_chunks()` | **三级切分**：标点断句 → 超长句硬切 → 攒块 |
| `text_to_speech_edge()` | 微软在线语音，失败自动重试 2 次 |
| `text_to_speech_gpt_sovits()` | 本地克隆，带重试与错误分类 |
| `prepare_refer_audio()` | 参考音频转 32kHz 单声道、时长校验 |
| `_match_loudness()` | 响度对齐（限制调整幅度 ±12dB，防止噪声被放大） |
| `generate_audio_from_script()` | 主流程调度 |
| `check_gpt_sovits_status*()` | 服务探活（探 `/docs` 静态页，不触发推理） |

**两个关键技术点**：

1. **不烧显卡的探活**：服务的 `GET /?text=...` 接口会真的执行一次语音合成，
   用它做健康检查等于每检查一次就白白跑一次推理。改为访问 `/docs`
   （框架自带的接口文档页，纯静态），实测 10 次探活共耗时 0.02 秒，GPU 占用不变。

2. **格式统一后再拼接**：不同来源的音频采样率和声道数可能不同
   （微软 24kHz、本地克隆 32kHz），必须先统一再相加，否则会报错或产生变调。

### `config.py` —— 配置中心（约 190 行）

所有可变项的**唯一出口**：

- 路径自动定位（以代码文件位置为基准，换盘换目录不受影响）
- 语音引擎位置自动探测（项目内优先，其次读 `.env` 指定）
- 相对路径自动补全为绝对路径（避免引擎在自己的目录里找错文件）
- 模型权重、推理参数、输出目录、界面绑定地址

### `logger.py` —— 日志（约 60 行）

- 同时输出到文件（详细）和控制台（简洁）
- 按 2MB 轮转，保留 5 个备份，不会撑满硬盘
- 修正 Windows 控制台编码，保证中文和符号正常显示
- 压制第三方库的冗余输出

### `check_env.py` —— 环境自检（约 230 行）

8 个检查组：Python 版本 → 依赖库 → ffmpeg → 语音引擎文件 → 显卡 →
密钥配置 → 端口占用 → 输出目录可写。
密钥只显示前后各 4 位，避免日志泄露。

## 四、语音引擎的集成方式

采用 **HTTP 服务调用**，而非直接导入库：

```
Python 主程序（gradio, 端口 7860）
      │
      │  POST http://127.0.0.1:9880/  {text, refer_wav_path, prompt_text, ...}
      ▼
GPT-SoVITS 服务（独立进程，端口 9880，自带 Python 3.9 + torch 2.0 + CUDA）
      │
      │  返回音频二进制流
      ▼
   写入 wav 文件 → pydub 处理
```

**为什么用独立进程而不是直接调用**：

| 好处 | 说明 |
|---|---|
| 依赖隔离 | 引擎需要 torch 等重量级库，主程序不需要，两者互不干扰 |
| 显存管理 | 模型常驻显存，避免每次合成都重新加载（加载一次约 10 秒） |
| 故障隔离 | 引擎崩溃不会拖垮主程序，重启即可 |
| 可替换 | 换用其他 TTS 只需改 HTTP 接口，主程序不用动 |

**通信细节**：主程序启动引擎时通过命令行参数指定模型权重和参考音频，
之后每次请求在 JSON 里带上待合成文本；引擎返回 wav 二进制流。

## 五、关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 界面框架 | Gradio | 纯 Python 即可构建 Web 界面，无需前端知识 |
| 大模型接入 | OpenAI SDK + DeepSeek | 接口格式兼容，SDK 自带重试和超时 |
| 音频处理 | pydub + ffmpeg | pydub 接口简洁，ffmpeg 用引擎自带的免安装 |
| 配置管理 | 单一 `config.py` | 零基础用户也只需改一个文件 |
| 代码风格 | 纯函数，不用类 | 便于逐行理解；系统规模小，无需面向对象抽象 |

## 六、答辩可能被问到的问题

**Q：为什么要切句？不能一次性合成整段吗？**
A：长文本一次性推理会导致显存占用过高、甚至超时失败。
切句后逐块合成，每块显存占用可控；而且句间插入停顿能让听感更自然，
接近真人说话的节奏。

**Q：怎么保证不同来源的音频能拼在一起？**
A：拼接前统一到 32kHz / 单声道 / 16 位，再做响度对齐，
消除句与句之间音量忽大忽小的问题。

**Q：怎么判断语音服务是否可用？**
A：访问它自带的 `/docs` 接口文档页 —— 这是纯静态页面，
既能证明服务已启动，又不会触发推理浪费算力。

**Q：系统怎么保证能部署到别的机器？**
A：三层保障：① 代码中无硬编码盘符，路径以文件自身位置为基准；
② 语音引擎自带 Python 环境和 ffmpeg，无需在目标机重装；
③ 提供环境自检脚本，部署后一键验证 8 个检查项。

**Q：为什么用你自己的模型而不是原厂底模？**
A：底模没有学习过目标音色，只能靠参考音频做零样本克隆，相似度有限；
微调后的模型学习了目标声音的音色特征，合成结果更接近。
系统保留了一键切换开关，方便做 A/B 对比验证效果差异。
